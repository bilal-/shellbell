# Local mobile builds and internal distribution

Shellbell keeps Expo's libraries and native config plugins but does not require
EAS Build or EAS Submit. Builds can run locally or on GitHub-hosted runners through
[requested CI internal delivery](mobile-ci-releases.md). Upload an existing artifact
explicitly, or opt into a local build that uploads to an internal track after it
succeeds.

Push delivery uses native FCM/APNs tokens and direct relay provider adapters.
`expo-notifications` remains an on-device API; no Expo account, Expo project ID or
Expo push credential is required. The relay needs private provider credentials for
the app identity: see [push setup and rotation](self-hosting.md#notifications-are-a-separate-dependency).

## Prerequisites

- Node 22+, pinned pnpm (`corepack enable`), Java 21 and Android SDK for Android.
- macOS with Xcode and CocoaPods for iOS.
- Ruby 3.2+ on PATH (not macOS's system Ruby), the Bundler version in
  `Gemfile.lock`, then from the repo root:

```sh
pnpm install --frozen-lockfile
bundle config set --local path vendor/bundle
bundle install
bundle exec ruby apps/mobile/fastlane/test/release_config_test.rb
bundle exec ruby apps/mobile/fastlane/test/lanes_test.rb
node --test apps/mobile/scripts/local-build.test.mjs
```

Fastlane is pinned in Gemfile/Gemfile.lock. Use a current supported Ruby; keep tool
versions consistent across machines. Android/iOS generated projects, output,
keystores, local environment files and service-account credentials stay out of Git.
Native project generation must retain both notification and local-signing plugins.

## Private environment

Load these through your private shell/session configuration, not tracked files:

| Variable | Purpose |
| --- | --- |
| `SHELLBELL_BUILD_NUMBER` | Explicit positive integer, at most 2100000000 |
| `SHELLBELL_GOOGLE_SERVICES_FILE` | Absolute path to Firebase client JSON registered to `sh.bilal.shellbell` |
| `SHELLBELL_ANDROID_KEYSTORE` | Absolute path to Android signing keystore |
| `SHELLBELL_ANDROID_KEY_ALIAS` | Signing key alias |
| `SHELLBELL_ANDROID_STORE_PASSWORD` | Keystore password |
| `SHELLBELL_ANDROID_KEY_PASSWORD` | Key password |
| `SHELLBELL_APPLE_TEAM_ID` | Actual Apple signing team, independent of bundle namespace |
| `SHELLBELL_IOS_PROFILE` | Installed host App Store provisioning profile name |
| `SHELLBELL_IOS_NOTIFICATION_PROFILE` | Installed notification extension provisioning profile name |

For iOS, create real App IDs for `sh.bilal.shellbell` and
`sh.bilal.shellbell.notifications`, shared app group
`group.sh.bilal.shellbell.notifications`, and matching provisioning profiles.
Retain the shared notification keychain entitlement generated by the plugin.
Do not use a previous app's store record or edit an old Firebase client package name.
Keys and profiles need a private recoverable backup; the repository is not a backup.

Keep a private next-build-number record. Use monotonically increasing numbers
across versions and check store history before reserving one. Do not derive numbers
from commit counts: a fresh repository history is not a store version history.

## First-time TestFlight setup

Upload authentication and app signing need separate credentials:

1. In App Store Connect, open **Users and Access → Integrations → App Store
   Connect API → Team Keys**. An Account Holder or Admin can generate a team
   key with **App Manager** access for this internal-distribution workflow.
   If API access has not been enabled, the Account Holder must request it first.
   Save the Key ID, Issuer ID and downloaded `.p8` privately; the key can only
   be downloaded once. Team keys apply across the account's apps.
2. Create the Shellbell app record for `sh.bilal.shellbell`, record its numeric
   Apple ID, then create an internal TestFlight group and add the intended
   App Store Connect users as testers. Use that exact group name in the upload
   configuration.
3. Install an **Apple Distribution** certificate with its private key on the
   build Mac. Configure App Store provisioning profiles for both app IDs listed
   above, under the actual developer team, with their matching app-group and
   keychain entitlements. A development certificate or an upload API key cannot
   replace distribution signing.
   [Register the shared app group](https://developer.apple.com/help/account/identifiers/register-an-app-group/)
   `group.sh.bilal.shellbell.notifications` and associate it with both app IDs
   before generating the profiles. Confirm the downloaded profiles include that
   group and permit the generated shared keychain entitlement.

Convert the API key into Fastlane's private JSON format (`key_id`, `issuer_id`,
`key`, and `in_house: false` for the standard Apple Developer Program). Set the
signing and upload environment variables documented here. Back up the original
`.p8`, signing certificate with its private key, profiles and account identifiers
outside Git. Direct APNs delivery also needs its own provider key; an App Store
Connect API key does not authenticate push notifications.

See [Apple's API-key setup](https://developer.apple.com/help/app-store-connect/get-started/app-store-connect-api/),
[internal tester setup](https://developer.apple.com/help/app-store-connect/test-a-beta-version/add-internal-testers/)
and [Fastlane's API-key format](https://docs.fastlane.tools/app-store-connect-api/).

## Build without uploading

### Store listing content

The [listing review page](../apps/mobile/listing-review.html) gathers the English
App Store and Google Play copy, screenshots, graphics and field validation.
The editable source is [Fastlane metadata](../apps/mobile/fastlane/metadata/).
The [Apple upload review](../apps/mobile/apple-assets-review.html) labels each
App Store Connect slot and includes the separately uploaded header assets.
[Listing configuration](../apps/mobile/.listing-kit/listing.json) records the
approved URLs, categories, screenshot order, captions and image descriptions.
Google Play's category, privacy URL and contact details are console fields;
keep private contact and reviewer-access details outside Git. Release notes
must describe the selected candidate, and are not generated from the package
version alone. The store privacy declarations use [PRIVACY.md](../PRIVACY.md)
as their source.

Use [listing-kit](https://github.com/bilal-/listing-kit) to regenerate the review
and validate the assets. From the repository root, with `LISTING_KIT_SKILL`
pointing to its `skills/listing-kit` directory:

```sh
bash apps/mobile/.listing-kit/render-graphics.sh "$LISTING_KIT_SKILL"
bash "$LISTING_KIT_SKILL/scripts/validate/validate-listing.sh" apps/mobile
bash "$LISTING_KIT_SKILL/scripts/package/build-review.sh" apps/mobile
python3 apps/mobile/.listing-kit/package.py
bash "$LISTING_KIT_SKILL/scripts/package/install-review-hook.sh" apps/mobile
```

The optional local hook refreshes the main review page when listing inputs or
app configuration are staged. Rerun `package.py` to refresh the Apple upload
review and upload archives after changing assets. Packaging checks every selected screenshot and header's exact
size and RGB format, and fails if a requested set is missing. It neither uploads
assets nor releases an app.

Screenshots use the real app routes with an explicit, offline
[capture entry point](../apps/mobile/.listing-kit/entry.ts) and synthetic data.
That entry replaces computer connections and identity loading for the capture
process, and selects the presentation without a hardware keyboard. The normal
`expo-router/entry` package entry is unchanged. Capture
builds are disposable simulator/emulator artifacts, not distribution candidates
or evidence of working transport or notification delivery.

After native project generation and dependency installation, build the iOS
simulator app from `apps/mobile`:

```sh
ENTRY_FILE="$PWD/.listing-kit/entry.ts" xcodebuild \
  -workspace ios/Shellbell.xcworkspace -scheme Shellbell \
  -configuration Release -sdk iphonesimulator \
  -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath output/listing-kit/ios \
CODE_SIGNING_ALLOWED=NO
```

Keep the Expo scene-lifecycle plugin enabled when generating iOS projects for
Xcode 27. The generated manifest must name `EXExpoAppSceneDelegate`, and the
AppDelegate must provide its React Native factory. See the
[iOS 27 QA gates](../apps/mobile/QA.md#ios-27).

For Duo builds with Xcode 27.1, Expo's precompiled Swift modules may not
match the compiler. The checked-in `ios.usePrecompiledModules: false` setting
compiles Expo modules from source. Run `pod install` from
`apps/mobile/ios` with the intended `DEVELOPER_DIR`, then build using that Xcode.
This increases the first build's duration. A stale ExpoModulesJSI slice can also
cause an import failure: remove only that generated slice's `.build-hash` under
`node_modules/expo-modules-jsi/apple/Products/` and rebuild. Do not patch vendor
Swift interfaces or change the app version to resolve a compiler mismatch.

For Android, from `apps/mobile/android`, the capture-only Gradle initializer
selects the offline entry and a standalone, locally signed `localTest` variant:

```sh
./gradlew -I ../.listing-kit/android.init.gradle :app:assembleLocalTest
```

Install these builds only on dedicated simulators/emulators. Match the exact
App Store Connect slot: Dynamic Island large uses 1320×2868, Dynamic Island
medium uses 1206×2622, and Duo accepts 1398×2034 outer or 2007×2853 inner captures.
Use Xcode 27.1 with its iOS 27.1 runtime for Duo. List simulator displays with
`xcrun simctl io "$SIMULATOR_UDID" enumerate` and select the intended display
explicitly when capturing a device with more than one screen. Do not assume the
default screenshot display is the one showing the app.

The iPad viewport is 2064×2752, Android phone 1080×1920 and Android tablet
1920×1080. Set Android's viewport before launching so the app lays out its controls
at the target size. Use full-screen app mode on iPad. Do not crop away keyboards
or controls to meet an aspect ratio. Apple header assets are separate creative
PNGs at 5244×2950 or 3840×1646, generated under `store-assets/apple/en-US/`.

From the repository root, capture a family after installing its build:

```sh
bash apps/mobile/.listing-kit/capture.sh ios "$SIMULATOR_UDID" iphone "$LISTING_KIT_SKILL"
bash apps/mobile/.listing-kit/capture.sh ios "$MEDIUM_UDID" iphone-medium "$LISTING_KIT_SKILL"
bash apps/mobile/.listing-kit/capture.sh ios "$DUO_UDID" iphone-duo "$LISTING_KIT_SKILL" "$DUO_DISPLAY"
bash apps/mobile/.listing-kit/capture.sh ios "$IPAD_UDID" ipad "$LISTING_KIT_SKILL"
bash apps/mobile/.listing-kit/capture.sh android "$PHONE_EMULATOR_SERIAL" phone "$LISTING_KIT_SKILL"
bash apps/mobile/.listing-kit/capture.sh android "$TABLET_EMULATOR_SERIAL" tablet "$LISTING_KIT_SKILL"
```

The flows reset the capture app's data, use example computer/project names and
never send input to a computer. Raw captures and build logs stay in ignored
`apps/mobile/output/listing-kit/`; store images are flattened RGB PNGs under
Fastlane. Review every image after capture, then rerun listing validation and
the public-source audit. Do not use these flows on a personal installation.

### Signed candidates

From `apps/mobile`, with the appropriate private environment loaded:

```sh
bundle exec fastlane android build
bundle exec fastlane ios build
```

Android produces `android/app/build/outputs/bundle/release/app-release.aab`.
iOS produces `output/ios/Shellbell.ipa`. The build command generates native projects;
Android runs Gradle, iOS installs pods and archives/exports with Xcode via Fastlane.
No cloud builder is invoked. A missing key, push config or profile is a setup error,
not a reason to disable notification security or sign a release with the debug key.

Android Release builds enable R8 code shrinking, optimization and obfuscation,
plus unused-resource shrinking. The release-optimization config plugin preserves
these settings across native regeneration and selects the optimizing Android
defaults. Native dependencies supply their consumer keep rules; add narrowly
scoped rules for confirmed reflection or JNI requirements rather than retaining
every class. Debug builds keep their usual debugging behavior.

Retain `android/app/build/outputs/mapping/release/mapping.txt` with the exact AAB,
its checksum and source revision. A mapping from a different build cannot reliably
decode its crashes. Keep JavaScript source maps and native symbol records with the
same private release evidence. Qualify notifications, pairing, terminal rendering
and WebRTC on the optimized internal-testing artifact before public distribution.

For development-only native generation, `pnpm exec expo prebuild --no-install`
does not require upload credentials. A build without genuine push configuration
does not qualify notifications. Generating projects is not proof they compile.

## Standalone local Android test APK (ADB only)

For device testing without Metro, use a clearly named, debug-signed test variant;
do not weaken the production Release signing guard. After Android prebuild, add
this block after the plugins in the **generated, ignored** `android/app/build.gradle`:

```groovy
android.buildTypes.create('localTest') {
    initWith android.buildTypes.release
    signingConfig android.signingConfigs.debug
    matchingFallbacks = ['release']
    debuggable false
    versionNameSuffix '-local-test'
}
```

From `apps/mobile/android`, with a compatible `JAVA_HOME`, run:

```sh
./gradlew app:assembleLocalTest -PreactNativeArchitectures=arm64-v8a --no-daemon
```

This bundles JavaScript into `app/build/outputs/apk/localTest/app-localTest.apk`.
Normal mobile connections negotiate WebRTC and pause terminal traffic until a
direct route is ready. For owner transport diagnostics and failure drills, set
`EXPO_PUBLIC_SHELLBELL_DIRECT=1` on the build command. That flag exposes diagnostic
controls; it is not required to activate normal direct transport.
Prebuild can regenerate the native directory, so reapply the local-only block
after regeneration. Java 21 is the current Android build prerequisite and has
been used for standalone S22 test builds. Qualify other Gradle/CMake toolchains
separately.
Normal connections negotiate direct transport without this flag.

This variant is for ADB testing only, never store upload.

Verify APK identity, signature and bundled assets before targeting a device by
its exact `adb -s` serial. An application-ID change installs a separate app and
does not preserve the previous app's pairing. Keep the old app until the new APK
is ready; remove it only with explicit approval. Without genuine matching
Firebase client configuration and a relay configured for direct FCM, this test build cannot qualify push.

## Upload an existing artifact (internal testing only)

Set `SHELLBELL_CONFIRM_UPLOAD=internal` and `SHELLBELL_ARTIFACT` to the absolute
path of the verified artifact. Keep the matching `SHELLBELL_BUILD_NUMBER` set.

Android additionally requires:

- `SHELLBELL_PLAY_CREDENTIALS_PATH`: private Play service-account JSON with access
  to the new app, which must already be initialized in Play Console.
- `SHELLBELL_BUNDLETOOL_JAR`: local official bundletool JAR, used to inspect the
  AAB's package and version code before uploading. Obtain from the
  [official project](https://github.com/google/bundletool/releases), verify the
  release provenance, and record the version privately.

```sh
bundle exec fastlane android internal
```

This explicitly selects the **internal testing track**, not Internal App Sharing.
It refuses mismatched artifacts and non-increasing internal-track version codes;
Google also enforces uniqueness across tracks. It does not upload metadata/images
or promote any track. Check Play Console processing and tester installation after
upload; account/app initialization restrictions may require owner action.

iOS additionally requires:

- `SHELLBELL_ASC_API_KEY_PATH`: private Fastlane API-key JSON containing the real
  `key_id`, `issuer_id` and private `key`, readable only by the release user.
- `SHELLBELL_ASC_APP_ID`: numeric ID of the new bundle's App Store Connect record.
- `SHELLBELL_TESTFLIGHT_GROUP`: exact existing **internal** group name.
- `SHELLBELL_IOS_USES_NON_EXEMPT_ENCRYPTION`: optional `true` or `false`, after
  determining the build's export classification with Apple's questions.
  `false` declares an exemption from encryption documentation; Shellbell still
  encrypts its sessions. An unset value leaves the declaration pending in
  App Store Connect. Check the algorithms and intended distribution countries
  against [Apple's encryption guidance](https://developer.apple.com/help/app-store-connect/reference/app-information/export-compliance-documentation-for-encryption)
  before reusing a classification for a wider release.

```sh
bundle exec fastlane ios internal
```

The lane verifies IPA identity/build number and the actual store record, rejects
external groups, uploads without external beta submission, waits for processing,
assigns the build to the internal group and checks assignment. It never creates
testers or groups. Before assignment it checks the accepted build's encryption
compliance and internal testing state. A processing/export-compliance/account failure is not successful
tester delivery; resolve it in App Store Connect and verify installation. If an
upload succeeded but assignment failed, inspect the existing build in the console
rather than re-uploading identical bytes or inventing success.

## Build and upload in one command

Configure the signing and upload prerequisites above, set
`SHELLBELL_CONFIRM_UPLOAD=internal` and choose a fresh `SHELLBELL_BUILD_NUMBER`.
From `apps/mobile`, run the relevant command:

```sh
bundle exec fastlane android build_internal
bundle exec fastlane ios build_internal
```

These lanes check the upload configuration before building, remove the previous
artifact at the generated output path, then build and verify the new artifact
through the existing internal-upload lane. A failed build cannot upload stale
output. The lanes use the generated artifact rather than `SHELLBELL_ARTIFACT`,
which remains available for the separate existing-artifact upload commands.

Android stays on Play's internal testing track. iOS waits for processing and
checks assignment to the named existing internal TestFlight group. Builds do not
upload unless an upload lane is explicitly invoked; these commands do not enable
CI release automation or public distribution. The first Play app upload may need
Console initialization before the API can be used. See [Fastlane's Play setup
requirements](https://docs.fastlane.tools/actions/upload_to_play_store/).

A completed local build is not a store upload. Record the processed store build,
tester installation and notification delivery separately. Missing distribution
certificates, profiles, API keys or developer-account access must be supplied by
the release operator; source tests cannot qualify them.

## Verification and recovery

### Retire a previous app installation without duplicate notifications

Keep a **private** migration record for each physical phone and computer account:
old package/bundle ID, new ID (`sh.bilal.shellbell`), build number, and the complete
old/new phone pairing fingerprints. Do not record pairing secrets or QR payloads.
Use `shellbell devices` against the intended running service to capture its full
fingerprints before and after pairing. Compare the new fingerprint displayed in
the pairing approval with the phone; device display names are not unique.

During side-by-side QA, both apps can claim `shellbell://`. Open the intended app
explicitly and use its in-app QR scanner; do not rely on a camera/deep-link chooser.
On Android, confirm the installed package and launch its explicit package/activity
with adb. On iOS, confirm the build/bundle in Xcode's device tools or TestFlight
before opening it. Stop if the app or fingerprint cannot be identified confidently.

Verify the **new** enrollment first: terminal read/input, reconnect, and a meaningful
notification while backgrounded. Then open desktop Settings → Devices, select the
superseded enrollment by its **complete fingerprint**, and verify the same fingerprint
in the revoke confirmation. This uses exact-fingerprint revocation, unlike the CLI's
`unpair` command, which also accepts names/prefixes. Do not remove all devices or use
a shared display name. Keep unrelated phones and other computer accounts enrolled.

Keep the service relay-connected during revocation. It removes that phone's local
pairing and tells the relay to remove its pairing/push registration and queued push
work. Confirm the old fingerprint is absent from `shellbell devices`, the new one
remains, the old app cannot reconnect, and a fresh event reaches only the new app.
Previously delivered OS notifications may remain; dismiss them separately. Repeat
for each computer paired with the retired app. Only then uninstall the exact old
package, preserving any unrelated installation. If relay delivery or identity is
uncertain, pause retirement and keep the private mapping for recovery.

After iOS prebuild, verify archive signing without a store upload:

```sh
bundle exec ruby apps/mobile/fastlane/test/native_signing_test.rb
```

This checks generated Release settings for both host and notification targets
before archive and leaves Debug signing unchanged. Actual installed certificates,
profile entitlements, signed archive/export, and device notification delivery still
require separate validation.

Run workspace lint/types/tests/build, Expo Doctor, generated asset checks and native
tests before distribution. Audit extracted artifact metadata separately from source.
Keep artifact hashes, build numbers, tool versions and actual device results in the
release record; keep account details private. Signing/store attribution can be
visible to recipients. Changing a bundle ID does not hide the legitimate signer.

Useful checks: `bundle exec fastlane lanes`, `node scripts/check-public-source.mjs`
(from root), and the [live release checklist](before-first-release.md). Do not enable
release workflow flags merely to use these local commands.
